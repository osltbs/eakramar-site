# eakramar-site — статический сайт с CI/CD

Сайт-визитка в Docker с полным конвейером сборки и доставки на боевой сервер.
Каждый push в ветку собирает образ, проверяет его на уязвимости и разворачивает
на VPS — без ручных действий.

**Живой сайт:** [eakramar.ru](https://eakramar.ru)

---

## Что показывает проект

Не «hello world из туториала», а работающий CI/CD на self-hosted инфраструктуре:

- **свой образ** сайта из Dockerfile — nginx со встроенной статикой
- **пайплайн** GitLab CI: сборка → сканирование → деплой
- **self-hosted GitLab** на Proxmox, раннер с Docker в LXC
- **деплой без простоя** на боевой VPS с TLS и автообновлением сертификата

## Конвейер CI/CD

```
git push → GitLab →
  ┌─────────┐   ┌────────┐   ┌──────────┐
  │  build  │ → │  scan  │ → │  deploy  │
  └─────────┘   └────────┘   └──────────┘
   собрать       trivy по      rsync на VPS +
   образ,        образу,       пересборка,
   в реестр      HIGH/CRIT     сайт обновлён
```

### build
Собирает Docker-образ из Dockerfile, сохраняет в GitLab Container Registry
и как артефакт для следующей стадии. Флаг `--provenance=false` — совместимость
формата образа с реестром.

### scan
[Trivy](https://trivy.dev) сканирует собранный образ на уязвимости уровня
HIGH и CRITICAL. Trivy запускается как образ стадии, читает tar-артефакт из build —
без обращения к реестру и Docker-сокету.

### deploy
Раннер по SSH синхронизирует код на VPS (`rsync`) и запускает пересборку
(`docker compose up -d --build`). Образ собирается на самом VPS из свежего кода.
SSH-ключ хранится в защищённых переменных CI (base64), секреты на VPS
исключены из синхронизации.

## Инфраструктура

Весь стек развёрнут самостоятельно, на своём железе:

```
Физический сервер
└── Proxmox VE (гипервизор)
    ├── ВМ: GitLab CE          сервер CI/CD, реестр образов
    └── LXC: GitLab Runner     executor docker, собирает образы

VPS (белый IP)
└── nginx в Docker             сайт eakramar.ru
    ├── TLS Let's Encrypt      webroot, автообновление
    ├── systemd                автозапуск стека
    └── firewall iptables      DROP по умолчанию
```

Раннер запускает Docker-в-Docker внутри LXC — с настройкой привилегий
(nesting, cgroups, AppArmor) для работы контейнеров во вложенной среде.

## Стек

- **GitLab CE** — репозиторий, CI/CD, Container Registry
- **GitLab Runner** — executor docker
- **Docker / Compose** — сборка и запуск

## Как это работает от коммита до сайта

1. Правишь код, `git push` в ветку `ci-cd`
2. GitLab видит `.gitlab-ci.yml`, запускает пайплайн
3. Раннер собирает образ, кладёт в реестр
4. Trivy проверяет образ на уязвимости
5. Раннер по SSH заходит на VPS, синхронизирует код, пересобирает
6. Сайт [eakramar.ru](https://eakramar.ru) обновлён

Ручных действий — ноль. От `git push` до живого сайта всё автоматически.

## Решённые задачи

Проект собран через реальные инженерные проблемы, а не по готовому рецепту:

- **Docker в LXC** — вложенная виртуализация требует nesting, доступа к cgroups
  и обхода AppArmor; настроено на уровне конфига контейнера Proxmox
- **Формат образа для реестра** — buildx по умолчанию создаёт attestation-манифесты,
  несовместимые со встроенным реестром; отключено `--provenance=false`
- **Trivy без сокета** — сканирование tar-артефакта вместо обращения к Docker
  или приватному реестру
- **SSH-ключ в CI** — многострочный ключ ломался в переменной GitLab;
  решено кодированием в base64
- **Деплой на боевой сайт без простоя** — rsync + пересборка на месте,
  секреты исключены из синхронизации

---

## Что можно развить

- перенос деплоя на `main` с ручным подтверждением (`when: manual`)
- environments в GitLab для отслеживания версий на проде
- rollback-стадия на предыдущий образ из реестра
- уведомления о статусе пайплайна
